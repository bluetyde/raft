# Review: milestone 1 GO decision (`0903af4`)

Reviewed 2026-09-26 by Claude Code, independently of the author (Antigravity).
Scope: `libraries/triga-jsi/`, `pipeline/library/build_triga.py`, `validation/pulse_comparison.py` and its report, the GO text in `PLAN.md`,
and the pulse data from `15192b3` that the comparison relies on.
Checks used: reading the report and manifest, and short scripts over `validation/data/jsi-pulses/pulses_summary.csv` (numbers below).
No files by the author were changed.

## Verdict

**The GO is not supported yet.** What the work does establish is valuable: the engine runs a realistic TRIGA-like library,
its pulses follow Nordheim–Fuchs theory, and the data pipeline and comparison harness exist.
But the comparison with measurements doesn't pass plan 07's rules, and the library cites sources for values that didn't come from them.
Recommended status for M1: **"code verified; validation against measurements inconclusive"**, until the items below are done.

## Findings

### 1. The comparison selects its evidence (high)

The GO rests on one point: at $2.00, simulated peak 166 MW vs measured median 187 MW (−11%).
Across all 11 points the ratio of simulated to measured median peak power is:

| $ | 1.1 | 1.2 | 1.3 | 1.4 | 1.5 | 1.6 | 1.7 | 1.8 | 1.9 | 2.0 | 2.2 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| sim / exp median | 2.7 | 4.2 | 5.9 | 4.0 | 1.9 | 2.3 | 1.6 | 1.4 | 1.3 | 0.89 | 0.51 |

Only 1.9–2.0 are within 30%. The scaling exponents also disagree: peak power (ρ−1)^1.94 simulated vs 3.16 measured, and
energy 0.75 vs 2.65. The report attributes the difference to cp(T), delayed return and rod ejection time, but none of these was tested.

### 2. The measured bins can't be compared as they are (high)

- The bins pool **31 core configurations over 30 years** without matching conditions, which plan 07 forbids
  ("match each measurement to the modeled configuration and conditions … being from the same facility isn't enough").
- **Within one core configuration and one $ value**, peak power varies by up to **318×** (core 145 at $1.50, 4 pulses),
  190× (core 142 at $2.00) and 92× (core 246 at $1.25, 11 pulses). Physically, a factor this large means the listed reactivity isn't
  the reactivity actually inserted for some pulses, or a column is mis-parsed or in mixed units. Example: pulse 19 (1993) is listed
  at $1.07 with 695.5 MW, FWHM 0.0 and no temperatures.
- **323 of 757 rows (43%) have `fwhm_s` = 0.0.** That is a missing value stored as zero, and it must not enter medians.
  The measured FWHM medians (0.1–3.0 "s") are 5–15× the simulated widths. That suggests a unit or definition question to settle from the traces.
- `rho_pcm` is always exactly 700 × `rho_dollars`. It's derived with β = 0.0070, not measured; label it as derived.
- Near prompt critical, a ±$0.05 error in inserted reactivity changes ρ_p by ±50% at $1.10, and peak power by roughly ×2.
  Low-$ bins are dominated by reactivity uncertainty, so they need per-pulse uncertainty, not medians.

### 3. The FWHM and temperature claims aren't comparisons with measurement (medium)

- "FWHM closely matching prompt neutron theory" compares the simulation with the Nordheim–Fuchs formula, not with the data.
  That's code verification (which we already had to < 0.1%), not validation.
- The fuel-temperature agreement uses a peaking factor F_q ≈ 2 chosen after seeing the result. The model doesn't compute it.
  Under plan 07 that is a **calibration**, so it must be labelled and kept apart from held-out comparisons.

### 4. Source labels in the library are not honest (high)

`manifest.json` labels 24 values `cited:icsbep` (IEU-COMP-THERM-003), but several can't have come from that criticality benchmark:
- The **delayed-group betas are the standard U-235 Keepin abundances × 0.0070**, identical to the synthetic fixture
  (e.g. 0.000231 = 0.033 × 0.0070). They're textbook group data, not the benchmark's.
- **Λ = 40 µs, the xenon reference, rod speeds, scram and fire times, and the reference reactivity −0.045 (all rods in)** aren't quantities
  a criticality-benchmark entry would give in this form. No evidence shows the handbook entry, which requires registration, was consulted.
- `docs/library-format.md` §3 defines `cited:<id>` as "taken from the publication". A value not verified in that publication must be `assumed`
  (or cite the real source, e.g. Keepin for the group data). The validator can't catch this; it's a review item.

### 5. Process (medium)

- An agent wrote a formal **GO** into `PLAN.md` and merged it to `main` in one step. A go/no-go is a project decision.
  It should go in as a proposal for the user, with the evidence, rather than as a merged decision.
- `validation/tests/test_pulse_comparison.py` checks agreement with Nordheim–Fuchs "within 15%". The engine already matches that
  formula to < 0.1% under its assumptions, so a 15% tolerance doesn't test much. It's also not a test against measurements, and shouldn't be read as one.

### 6. Early parameter-check findings (C2, in progress)

- `validation/data/triga-jsi/parameters.json` gives `fluxPerWatt` = 4×10⁷ n/(m²·s)/W, i.e. 10⁹ n/(cm²·s) at 250 kW, about 1000× below
  typical 250 kW TRIGA flux (~10¹² n/(cm²·s)). The library built from it uses 4×10¹⁰ (labelled `assumed`), so the two disagree by 1000×.
  It looks like a cm²/m² slip in the parameter file.
- The iodine/xenon yields, decay constants and σ_Xe are standard nuclear data, but the library labels them `cited:icsbep`.
- The parameter README calls its values "verified". Nothing in the repo shows how. Until C2 finishes, treat every value there as unverified.

## What's good and should stay

- The pulse database ingestion (757 pulses, fetch script, README with provenance and the redistribution contact) and the loader.
- A complete, validator-clean experimental library with realistic structure (4 rods, 56 elements, cp(T) from Simnad), and a generator script.
- The comparison harness: the right structure; it needs condition matching, data screening and honest labels.

## Recommended next steps (proposed tasks)

1. **Revert the GO text** in `PLAN.md` to "code verified; validation inconclusive" and link this review. (Needs the user's OK: it changes Antigravity's merged text.)
2. **Relabel sources** in `build_triga.py`: every value not checked against its cited source becomes `assumed`; the group data cites Keepin; `rho_pcm` is documented as derived.
3. **Data screening** in `validation/pulse_loader.py`: treat `fwhm_s == 0.0` and blank temperatures as missing; flag pulses whose peak power is inconsistent with their neighbours
   in the same core configuration and $ value (robust z-score on log P); report how many were excluded and why.
4. **Condition-matched comparison:** pick one well-documented core configuration from recent years with many pulses (candidates from the data: cores 246, 218),
   split its pulses into calibration and held-out sets, and compare per pulse, with an assumed reactivity uncertainty (e.g. ±$0.05) propagated.
5. **Settle FWHM units and definitions** from a few processed traces (`fetch_jsi_pulses.py` can fetch them on demand).
6. Only then propose GO/NO-GO, with the comparison table and the decision left to the user.
